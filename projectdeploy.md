# Billing Agent Deployment Guide

## 1. Goal

This guide explains exactly how to deploy this project in a production-style setup.
If you follow it step-by-step, you can deploy:

- API service
- MCP HTTP service
- Database migration job
- Health-verified rollout

The repository uses GitHub Actions CD and Docker images in GHCR.

---

## 2. Deployment Model Used by This Repo

From `.github/workflows/cd.yml`, deployment works like this:

1. Build Docker image from repository.
2. Push image to GHCR (`ghcr.io/<owner>/billing-agent`).
3. On production job, use self-hosted runner with labels:
- `self-hosted`
- `linux`
- `x64`
- `billing-prod`
4. Authenticate to Azure using GitHub OIDC.
5. Pull secrets from Azure Key Vault.
6. Generate `.env.production` on runner.
7. Deploy API + MCP containers using `deploy/compose.prod.yml`.
8. Run `alembic upgrade head` in a one-shot container.
9. Verify health endpoints.

---

## 3. What Gets Deployed

The deployed runtime contains two services from same image:

1. API container
- Command: `uvicorn src.api.main:app --host 0.0.0.0 --port 8000`
- Port: `8000`

2. MCP container
- Command: `uvicorn mcp_server.http_api:app --host 0.0.0.0 --port 9000`
- Port: `9000`

Definition file: `deploy/compose.prod.yml`

---

## 4. Prerequisites Before First Deployment

You need all items below.

1. GitHub repository admin access
- Required to configure environments, variables, and secrets

2. Azure subscription and Entra app for OIDC
- Required by `azure/login@v2` in deployment workflow

3. Azure Key Vault
- Stores runtime secrets consumed during deploy

4. Production host with self-hosted GitHub runner
- Linux x64 machine
- Docker and Docker Compose installed
- Network path to DB / required infrastructure

5. Branch protections and environment approval policy
- Recommended for controlled production releases

## 5. GitHub Setup (One-Time)

### Step 1: Confirm Actions and Packages are enabled

In repository settings:

- Actions enabled
- Packages enabled
- GITHUB_TOKEN has package write through workflow permissions

### Step 2: Create GitHub Environment

Create environment named `production` and require reviewer approval.

Add environment variables (GitHub Environment -> Variables):

- `AZURE_KEY_VAULT_NAME`
- `AUTH_INTROSPECTION_URL`
- `AUTH_INTROSPECTION_CLIENT_ID`
- `AUTH_ROLE_CLAIM`
- `AUTH_SCOPE_CLAIM`
- `AUTH_READ_ROLE`
- `AUTH_WRITE_ROLE`
- `AUTH_APPROVE_ROLE`
- `AUTH_ADMIN_ROLE`
- `LLM_MODEL`
- `LITELLM_BASE_URL`
- `MCP_CLIENT_MODE`
- `MCP_SERVER_URL`

Add environment secrets (GitHub Environment -> Secrets):

- `AZURE_CLIENT_ID`
- `AZURE_TENANT_ID`
- `AZURE_SUBSCRIPTION_ID`

### Step 3: Configure Azure OIDC trust

Create federated credential in Entra App:

- Issuer: GitHub OIDC issuer
- Subject tied to this repo and `production` environment
- Audience: `api://AzureADTokenExchange`

This allows GitHub job to log in without long-lived cloud credentials.

### Step 4: Create required Key Vault secrets

Key Vault secrets expected by workflow:

- `billing-database-url`
- `billing-mcp-service-token`
- `billing-introspection-client-secret`

These are loaded at deploy time and written into `.env.production` on runner.

## 6. Production Host Setup (One-Time)

On target Linux host:

1. Install Docker Engine and Docker Compose plugin.
2. Install self-hosted GitHub runner.
3. Register runner for this repository.
4. Add labels exactly:
- `self-hosted`
- `linux`
- `x64`
- `billing-prod`
5. Ensure runner service auto-starts.
6. Ensure host can pull from `ghcr.io`.

Optional but recommended:

- Reverse proxy + TLS in front of ports 8000 and 9000
- Firewall restrictions
- Log rotation

## 8. Docker Image Lifecycle and Tagging

Image name pattern:

- `ghcr.io/<repo_owner>/billing-agent`

Tags generated by workflow metadata step:

- `sha-<commit_sha>` (immutable rollout tag)
- `vX.Y.Z` (when tag push happens)
- `latest` (default branch)

Deployment uses `sha-<github.sha>` for deterministic releases.

## 9. Full Functional Deployment Example

This is the exact release flow using current automation.

### Example assumptions

- Repo owner: `acme-org`
- Target branch: `main`
- GitHub environment: `production`
- Runner labels configured correctly

### Step-by-step

1. Merge tested PR to `main`.
2. GitHub CD workflow triggers automatically.
3. `build-and-push` job publishes image:
- `ghcr.io/acme-org/billing-agent:sha-<commit>`
4. `deploy-production` waits for environment approval.
5. Approver approves `production` deployment.
6. Job logs into Azure via OIDC.
7. Job pulls Key Vault secrets.
8. Job writes `.env.production` containing:
- DB URL
- MCP service token
- OIDC introspection client secret
- role/scope vars
- LLM/MCP settings
9. Job logs in to GHCR and pulls rollout image.
10. Job runs:

```bash
docker compose -f deploy/compose.prod.yml --env-file .env.production pull
docker compose -f deploy/compose.prod.yml --env-file .env.production up -d --remove-orphans
```

11. Job runs migration:

```bash
docker run --rm --env-file .env.production ghcr.io/acme-org/billing-agent:sha-<commit> alembic upgrade head
```

12. Job validates health:

```bash
curl --fail --retry 12 --retry-delay 5 http://localhost:8000/health/ready
curl --fail --retry 12 --retry-delay 5 http://localhost:9000/health/live
```

13. Deployment is complete.

## 10. Deploying to Different Places (API and MCP Split)

Current default deploys API and MCP on same host.
You can split them if needed.

How:

1. Deploy API on host A.
2. Deploy MCP on host B.
3. Set API env:
- `MCP_CLIENT_MODE=http`
- `MCP_SERVER_URL=https://mcp.yourcompany.com` (or internal URL)
4. Keep same `MCP_SERVICE_TOKEN` on both sides.
5. Expose MCP endpoint securely (TLS + restricted network).

Practical recommendation:

- Start with same-host deployment.
- Split only when scaling/security boundaries require it.

## 11. Rollback Procedure (Functional Example)

If latest deploy fails after release:

1. Identify previous healthy commit SHA.
2. Re-run CD workflow from that commit (or trigger manual workflow at older ref).
3. Ensure `BILLING_IMAGE` resolves to previous `sha-` tag.
4. Re-run compose pull/up steps.
5. Verify health and key business API request.
6. Keep incident notes with exact image digest and timeline.

Important:

- Prefer backward-compatible migrations.
- If non-backward-compatible schema exists, prepare explicit rollback migration plan.

## 12. Post-Deployment Verification Checklist

Run these checks after every deploy:

1. Health endpoints
- `GET /health/ready` on API
- `GET /health/live` on MCP

2. Observability
- `GET /metrics` on API

3. Functional smoke test
- Send one valid `POST /api/chat` request with authorized credentials

4. Approval flow smoke test
- Trigger one approval-required case and process approval decision

5. Logs
- Verify no repeated 5xx or auth failures

---

## 13. Common Deployment Failures and Fixes

1. Azure login failure in workflow
- Check OIDC federated credential subject and environment mapping.

2. Key Vault secret fetch fails
- Verify vault name variable and access policy/RBAC for Entra principal.

3. GHCR pull failure on runner
- Verify docker login step and package permissions.

4. API cannot reach MCP
- Validate `MCP_SERVER_URL`, network route, firewall, token alignment.

5. Migration failure
- Verify `DATABASE_URL`, DB user permissions, and migration history state.

---

## 14. Best Practices You Should Follow

1. Use immutable image tags for deploys (`sha-*`), not floating tags.
2. Keep production secrets in Key Vault only.
3. Require GitHub environment approvals for production.
4. Run CI quality gates before merge.
5. Keep migrations safe and reviewed.
6. Keep API and MCP health checks in deployment pipeline.
7. Use principle of least privilege for GitHub, Azure, and runner host.
8. Document every production change in PR and release notes.

---

## 15. Minimum Runbook for New Joiner

If you are new and need shortest deploy path:

1. Confirm GitHub environment and Azure OIDC are already configured.
2. Confirm Key Vault has required 3 secrets.
3. Confirm self-hosted runner with `billing-prod` label is online.
4. Merge PR to `main`.
5. Approve production environment when prompted.
6. Wait for CD workflow to complete.
7. Verify `/health/ready`, `/health/live`, and `/metrics`.
8. Execute one billing chat request as final smoke test.
